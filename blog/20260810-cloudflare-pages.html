会社のホームページは無料枠で足りる、新しく作るならWorkersから

2026.08.10 夕（2026.11.02 更新）｜ 株式会社NGraph

会社のホームページは、Cloudflareの無料枠で足ります。ngraph.jpも、ファイル数の上限に対して3.4%しか使っていません。

ただし、この記事の8月の版から変わったことが2つあります。当社は2026年8月にPagesからWorkersへ移りました。

そしてCloudflareの公式ページは、新しい案件をWorkersから始めるよう案内しています。

この記事では、無料枠で実際に足りるのか、PagesとWorkersのどちらを選ぶか、移して何が変わったかを書きます。

Cloudflareには、サイトの置き場所が2つある

どちらも、作り終えたサイトのファイルをCloudflareの世界中のサーバーに置いて配る仕組みです。Pagesはサイトを置く専用の場所で、Workersはサーバー側の処理も動かせる場所です。

従来のレンタルサーバーとの違いは、サーバーを借りて手でファイルを置かないことです。Git（ファイルの変更履歴を管理する仕組み）に送ると、自動で配られます。

置き場所置くもの更新の仕方静的ファイル配信の課金向く用途
レンタルサーバーFTP等で手動アップロードファイルを1つずつ差し替え—更新頻度が低いサイト
Cloudflare PagesGitリポジトリpushすると自動ビルド・自動反映静的ファイルへのリクエストは無料・無制限（公式原文）更新頻度が高いサイト
Workers Static AssetsGitリポジトリ＋Workerpushすると自動ビルド・自動反映静的ファイルへのリクエストは無料・無制限（公式原文）サーバー側の処理も要るサイト

レンタルサーバーの料金は検証していないため、この記事では書きません。Cloudflare側の課金の考え方だけが、公式ドキュメントで確認できる範囲です。

無料枠の上限と、当社の実測

会社のホームページ程度の規模なら、ファイル数と容量の上限には届きません。Workersの無料枠の上限と、ngraph.jpの実測を並べます。

ファイル数20,0006833.4%

Pagesを使う場合は、ここにビルド回数の上限が加わります。無料プランは月500回で、毎日更新するサイトほど先に近づきます。

当社の直近30日のcommit数は157件です。今はPagesのビルドではなく、GitHub Actionsから公開しています。

Workersで気をつけるのは、1日10万リクエストの上限です。静的ファイルへのリクエストは無料で無制限ですが、当社のようにrun_worker_firstで全リクエストに処理を通すと、この上限に数えられます。

超えると、公式の説明では429エラーが返ります。

同じ「20,000ファイル」でも、PagesとWorkersでは数える単位が違う

Cloudflare公式ドキュメント（2026年11月2日参照）を突き合わせると、Pagesは「1サイトあたり20,000ファイル」、Workers Static Assetsは「1 Workerバージョンあたり20,000ファイル」という単位で上限が決まっています。

プロジェクト数の上限にも違いがあります。

Pagesは1アカウントあたり100プロジェクトで、公式原文には "This limit is not routinely increased."（この上限は日常的には引き上げられない）と明記されています。

一方Workersは無料プランで1アカウント100 Workers、有料プランでは500 Workersです。

Pagesの上限ページは、100サイトを超える場合はWorkers for PlatformsまたはWorkers Static Assetsを検討するよう案内しています。

ただし数える単位そのものが違うため、「どちらが多いか」という単純な比較は成立しません。比べるべきは数の大小ではなく、「何を1つと数えるか」です。

公式は、新しい案件をWorkersへ案内している

Pagesの公式トップには、今こう書かれています。「Start new projects with Workers.」（新しいプロジェクトはWorkersで始める）。

同じ箇所で、Workersを「Cloudflare's primary platform」（Cloudflareの主要な基盤）と呼んでいます。

8月の時点で確認した範囲では、この案内は見当たりませんでした。ただし確認した公式ページに、Pagesの廃止を告げる記述はありません。

すでにPagesで動いているサイトを、急いで移す理由にはなりません。

この移行ガイドが持つ互換表（compatibility matrix）を数えると、Workersだけが対応している機能は15件（Cron Triggers・Workers Logs・Logpush・Tail Workers・Source Maps・Queue Consumers・Rate Limiting・Email Workers・Image Resizing・Gradual Deployments・Remote Development・Quick Editor in Dashboard・Cloudflare Vite plugin・パス配下への静的配信・ルート直下以外への配置）、Pagesが上でWorkersは部分対応にとどまる機能は5件（Early Hints・Branch Deploy Controls・Custom Branch Aliases・ファイル配置がそのままURLになる仕組み〈File-based Routing〉・Pages Plugins）、Pagesだけが対応している機能は1件です。

機能の数ではWorkersが広い。判断を決めるのは1件

判断を決めるのは、Pagesだけが対応している1件です。

それはCloudflareで管理していないドメインを独自ドメインとして使えること（互換表の原語では "Custom domains outside Cloudflare zones"）です。

公式は「Workersはネームサーバーが Cloudflare で管理されていないドメインに対応しない」と説明しています。

ドメインを制作会社や既存のレジストラなど他社に預けたままの会社にとって、この1件が移行できるかどうかをそのまま決めます。数の多寡ではなく、自社に該当する1行があるかで判断が決まるということです。

当社がつまずいたのは、URLの末尾だった

Cloudflare Pagesの配信仕様（2026年8月10日参照）には次のように書かれています。

「Pages will also redirect HTML pages to their extension-less counterparts: for instance, `/contact.html` will be redirected to `/contact`, and `/about/index.html` will be redirected to `/about/`.」（Pagesは、`.html` で終わるページを拡張子なしのURLへリダイレクトする。

例えば `/contact.html` は `/contact` へ、`/about/index.html` は `/about/` へ転送される）。ただし、公式にはこのリダイレクトのステータスコードが書かれていません。

私たちの一次体験：実際にcurlで測ると、`https://ngraph.jp/blog/what-is-fde.html` は307を返し、リダイレクト1回で `https://ngraph.jp/blog/what-is-fde` が200に着きます。Workersへ移したあとの2026年11月2日に測っても、307は同じでした。問題は表示ではありません。表示は正常に出るので誰も気づきません。問題は、サイトが自分で名乗るURL——検索エンジンに「正式なURLはこれです」と伝えるcanonical指定や、サイトマップに載せるURL——が `.html` 付きのまま残ることでした。正式なURLとして名乗った先が、実際には転送されるURLになっていたのです。1回直しても、新しいページを作るたびに元に戻りました。手で守るのをやめて、公開の手前に機械の検査を置きました。拡張子なしに揃っているかを自動で確認し、揃っていなければ公開させない仕組みです。ここから引き出せる一般化は、置き場所を変えると、料金や速度ではなくURLの見え方のような細部が最初に効いてくるということです。そして細部は人の注意力では守れません。

始めるときの手順と、どこで詰まるか

段階やること詰まりやすい点
1. アカウント作成Cloudflareのアカウントを作る—
2. Git連携サイトのファイルをGitに置く初めてGitを使う場合は変更履歴の考え方に慣れが要る
3. プロジェクト作成Workersのプロジェクトを作る設定を誤ると反映されない
4. ドメイン接続独自ドメインをつなぐネームサーバーをCloudflareへ移す必要がある
5. 検査を仕組みにする公開前の検査を自動化するURLの形など、目視では見落とす細部がある

費用の面では、静的ファイルへのリクエストは無料・無制限、保存にも追加費用はかからないと公式ドキュメントに書かれています。ただし「無料枠で足りる」は、ドメイン代と制作費が0円という意味ではありません。

無料なのはCloudflare側の配信の仕組みに限った話です。

よくある失敗

  1. URLの表記を `.html` のまま残す。表示は正常なので誰も気づきません。公開手順に機械の検査を入れて、拡張子なしに揃っているかを確認する必要があります。
  2. 無料枠を「容量」だけで確認して、回数を見ない。先に埋まるのは、Pagesならビルド回数、Workersなら1日のリクエスト数です。
  3. ドメインを他社で管理したままWorkers側へ移そうとする。互換表では、Cloudflare管理外のドメインはWorkers非対応の1件として明記されています。
  4. 会員機能や予約のようにサーバー側で処理が要るものを、静的なファイルを配る仕組みだけで作ろうとする。PagesもWorkers Static Assetsも、置いて配るのは静的なファイルです。サーバー側の処理には別の仕組みが要ります。
  5. 「Pagesはもう終わる」という噂だけで移行を急ぐ。公式は新しい案件をWorkersへ案内していますが、確認した範囲に廃止の記述はありません。この領域の案内は3か月で変わります。いつ時点の話かを必ず確認してください。

よくある質問

Cloudflare Pagesは本当に無料で使えますか？

静的ファイル（あらかじめ作り終えた画像やHTMLなど、閲覧のたびに作り直さないファイル）へのリクエストは無料・無制限だと公式ドキュメントに明記されています。保存にも追加費用はかかりません。ただし無料プランにはファイル数・1ファイルの容量・月間ビルド回数の上限があり、ドメイン代や制作費が無料になるという意味ではありません。

更新のたびにビルドが走ると、無料枠の月500回はいつ足りなくなりますか？

更新の頻度で決まります。ngraph.jpの直近30日のcommit数は157件で、1回の更新に複数のcommitが乗ることもあります。毎日更新しても月500回の上限には届きにくい水準です。なお当社は現在Workersで配信しており、Pagesのビルド回数は使っていません。

いま新しく始めるなら、PagesとWorkersのどちらを選べばいいですか？

公式はWorkersから始めるよう案内しています。例外は、ドメインのネームサーバーをCloudflareへ移せない場合です。その場合はPagesを使います。

他社で管理している独自ドメインでも使えますか？

Pagesは対応していますが、Workersの互換表ではCloudflareで管理していないドメインを独自ドメインとして使う機能（Custom domains outside Cloudflare zones）が非対応と示されています。ドメインを制作会社や既存のレジストラに預けたままの会社は、この1件が移行の可否をそのまま決めます。

会員機能や予約フォームのあるサイトも置けますか？

Pages・Workers Static Assetsのいずれも、置いて配るのは静的なファイルです。会員機能や予約のようにサーバー側で処理が要るものは、この仕組みだけでは作れず別の仕組みが必要になります。

Cloudflare Pagesはいずれ終わるという話を聞きましたが、本当ですか？

2026年11月2日に確認した公式4ページに、Pagesの廃止を告げる記述はありません。ただしPagesの公式トップは、新しいプロジェクトをWorkersで始めるよう案内しています。すでに動いているサイトを急いで移す必要はありませんが、新規ならWorkersを選びます。

まとめ

会社のホームページは、無料枠で足ります。新しく作るならWorkersから始め、すでにPagesで動いているならそのままで構いません。

移す前に確かめるのは1つです。自社のドメインのネームサーバーを、誰が管理しているかを確認してください。Cloudflare以外のままならWorkersへは移せません。
