AIが承認するClaude Shipの説明書には、書いた本人しか見ないまま通る設定が7つ並んでいる

2026.11.24 夕 ｜ 株式会社NGraph

AIが変更の承認まで受け持つ「Claude Ship」が出ました。

Anthropicが2026年11月23日に出したベータの仕組みです。同じ日に公開された公式の説明書は、設定しだいで、書いた本人以外は誰も見ないまま変更が通りうる場合を、例として7つ挙げています。

この記事の結論は、AIに承認を任せるかどうかを考える前に、「誰が見たら通してよいか」を自社の言葉で書き出すことです。変更を本線に直接入れている会社では、その変更にClaude Approvalsのチェックが付きません。私たちは福井市のNGraphという会社で、AI導入の現場に入っています。

この記事でわかること
・Claude Shipの3つの役割と、使える会社の条件
・説明書が挙げる7つの場合
・導入の前に自社で書き出す3つのこと

Claude Shipは3つのAIで、変更の見直し・修正・承認の判定までを受け持つ

先に言葉を開きます。GitHubは、変更履歴を置いて共同作業するサービスです。プルリクエストは、変更を「本線に入れてよいか」と提案する単位です。本線は、リポジトリの基準になる枝で、正式には既定ブランチといいます。提案を本線に取り込むことをマージと呼びます。

発表記事によると、Claude Shipは2026年11月23日からベータで提供されています。プルリクエストを見直し、直し、チームの方針にもとづいて「マージしてよいか」を判定する仕組みで、どの変更に人が要るかはチームが決めます。

名前やることやらないこと・注意提供の段階
Code Reviewプルリクエストを複数の観点で見直し、指摘を確かめて書き込む。深さはQuick、Standard、Deepから選ぶClaude Ship全体について、AIなので見逃すことがあると公式が明記している一般提供
PR Steward失敗した自動テストや衝突、レビューの指摘に対応して修正を入れ、変更点と戻し方をコメントする承認やマージはしない設計ベータ
Claude Approvals方針ファイルに従い、あと誰の承認が要るかを報告する。方針が許せば、定型的な変更はClaudeだけで承認できるマージを止められるのは、GitHubで必須にした場所だけベータ

表1　Claude Shipの3つの役割。出所はAnthropicの発表記事（2026年11月23日）とClaude Code Docs（2026年11月24日閲覧）

提供先は、ClaudeのTeamプランとEnterpriseプランで、GitHub上のリポジトリが対象です。データを保持しない設定や、顧客が管理する暗号鍵を使う組織では使えません。

Claude Codeのチームでは、6月から9月にかけてマージされたプルリクエストが2倍を超え、取り消された割合は40%超減ったと、Anthropicは書いています。ただしClaudeのレビューは工程の1層だと断った数字で、Claude Ship単体の成果ではありません。

説明書は「書いた本人しか見ないまま通る場合」を7つ挙げている

公式ドキュメント「Claude Approvals and your GitHub rules」の節「Merges without human review」は、Claude Approvalsを有効にしても、プルリクエストが書いた本人以外の誰も見ないままマージされうる、という内容です。ボットが書いたものなら、人が1人も見ないままマージされうるとも書いています。

ドキュメントが書く起き方は2つです。GitHubがチェックを必須にしていない場合と、本人以外の人がいなくてもチェックが通る場合です。では、後者の例とは何でしょうか。ドキュメントが箇条書きにしているのは、次の7つです。方針のseatsは、承認に必要な人数です。

  1. seats: 0。人数ゼロ。ボットが書いたプルリクエストは、人が誰も見ないままマージされることがあります。
  2. seats: 1。1人。その1人を書いた本人が埋められるので、ほかの誰も見ないままチェックが通ります。
  3. ボットを数に入れる一覧。誰を数えるかを並べるfromに、ボットを入れている場合です。
  4. マシンユーザー。スクリプトやエージェントが動かしているユーザーアカウントのことです。人として数えられることがあります。
  5. 席を引き継ぐ設定。追加の変更を送ったあとも、埋まった席を引き継ぐreuseの設定です。
  6. どのルールにも当たらないファイル。GitHubは「どちらでもない」という結果を、合格として数えます。
  7. 分類器の答えを読む条件。分類器は、AIに「この変更は危ないか」などを判定させる部品です。その答えは、プルリクエストの文章で誘導できるとされています。

ただし、7つは例です。全部で7通りしかない、という意味ではありません。また、seats: 2は2人という意味ですが、そのうち1人は書いた本人でかまいません。

止まるのは、必須かつ本人以外を求める1か所

このチェックがマージを止めるのは、右上の組み合わせです。GitHubでチェックを必須にしていて、方針が本人以外の人を求めている場合に当たります。残る3つは、このチェックの側からは本人だけで通りうる組み合わせです。GitHub自身の承認のルールは、この図に入れていません。

止める力を持つのはGitHub側の設定で、Claudeのチェックは「必須」にして初めて止まる

Claude Approvalsは、プルリクエストに付く「チェック」です。このチェックがマージを止めるのは、GitHub側で「必須のチェック」にした場所だけです。観察モードでは、通常は止めません。

同じ節には、7つとは別に、次の記述があります。

  • 本線への直接のpushには、チェックが付きません。pushは、変更をそのままリポジトリに送ることです。ドキュメントは、GitHub側でプルリクエストを必須にするよう書いています。
  • Claudeの承認は、GitHubの「承認1件が必要」というルールを満たすことがあります。
  • claude: approvesと書いたルールは、それだけではCode Reviewを起動しません。何もレビューしていない変更を、Claudeが承認しうるということです。
  • 自動マージやマージキュー（順番待ちで自動マージする仕組み）を、人の承認を求めない方針と組み合わせると、誰も操作しないままマージされることがあります。

ルールを緩められる人もいます。方針ファイルを変えられるのは、既定ブランチにマージできる人です。チェックを必須から外せるのは、GitHubのリポジトリ管理者です。

PR Stewardは承認もマージもしない設計です。Anthropicの用意した環境で動くとき、操作の扱いは次のとおり分かれます。

ブランチの削除Anthropic側が断る
タグのpushAnthropic側が断る
マージGitHubのルールに任せる
自動マージGitHubのルールに任せる
強制pushGitHubのルールに任せる
他のブランチへのpushGitHubのルールに任せる

小さい会社で最初に当たるのは「書き込める人が2人いるか」と料金

手順を書いたドキュメント「Set up Claude Approvals」の前提条件に、見落としやすい1行があります。このページの見本の方針を実施する前に、書き込み権限のある人が2人必要だと書かれています。

では、書き込める人が1人の会社はどうなるのでしょうか。1人しかいないと、.claude/以下の変更や、Claudeのレビューが落ちたとき、結果を返さなかったときに、チェックが通りません。「各変更に2人」という見本の方針では、どの変更でも通りません。

見本の方針は2つです。1つ目は「Code Reviewが通ったらClaudeが承認」で、実施すると、Claudeのレビューを通ったプルリクエストは通常、ほかの人の承認が要りません（.claude/以下は除く）。通らなかったものは通常、本人のほかに1人が必要です。2つ目は「各変更に2人」で、通常は本人のほかに1人が要り、Claudeは承認しません。

Claudeのレビューを通れば、他に要る人は通常0人

1つ目の見本の方針を実施すると、Claudeの見直しを通った変更は、通常、本人のほかに誰の承認も要りません。

そのうえで、料金の側にも先に知っておきたい点があります。

  • 課金はトークン量です。方針ファイルが既定ブランチに入ると、課金が始まりうると書かれています。
  • 観察モードも課金されます。Claudeのレビューを使う方針は、観察モードでもCode Reviewを起動するためです。
  • 組織の設定で使用クレジットをオフにしても、有効になっているエージェントは動き続け、課金も続きます。
  • PR Stewardには、設定するまで独自の支出上限がありません。Claude Approvalsの分類器の行も、設定画面に現れた時点では上限がありません。

人がふだん本線に直接入れている会社では、その変更はこの仕組みの目に入らない

自社の場合：私たちは、このブログを置いている自社サイトのリポジトリの履歴を数えました。変更は879件で、そのうちマージで入ったものは3件です。記事の公開は、公開前の機械検査を通したあと、本線へ直接pushしています。pushすると、そのまま本番に出ます。プルリクエストは経ていません。なお、私たちはClaude Shipを導入していない側の会社です。

そのため、この運び方のまま方針ファイルを置いても、公開の変更はチェックの対象になりません。本線への直接のpushには、チェックが付かないからです。AIに承認を任せるかどうかの前に、変更をプルリクエストに通す運び方に変えるかどうかが先に来ます。

Anthropicは多くの顧客に、まず観察だけのモード（observe）で有効にして、信頼を築いてから必須にすることを勧めています。観察モードのチェックは、方針ならどう判定したかを見せるだけです。前提がそろっていれば、方針ファイルを既定ブランチにマージできる人なら誰でも始められます。

では、導入の前に何を書き出せばよいのでしょうか。3つあります。

順番書き出すこと見る場所
1いま、変更を本線にどう入れているか。プルリクエストを通しているか、直接pushかリポジトリの変更履歴。マージで入った数と、直接入った数
2書いた本人以外の誰が見たら通してよいか。変更の種類ごとにドキュメントの例は、請求まわりのコードは2人、テスト用データはCode Reviewが通れば1人
3月の上限額と、止める手順。誰が止めるか設定画面の支出上限。止める順はApprovals、PR Steward、Code Review

よくある失敗・NGパターン

  • 観察モードで始めたつもりで、実施になっている。modeの行が無い方針ファイルは、実施されます。自分で書いた方針では、mode: observeの行を確かめます。
  • 「Claudeが承認」と書けば、レビューもされると思う。claude: approvesと書いたルールは、それだけではCode Reviewを起動しません。先にレビューさせるには、「Code Reviewが通ったときだけClaudeが承認」と書きます。
  • 使用クレジットを切れば、止まると思う。クレジットをオフにしても、有効なエージェントは動き続け、課金も続きます。止めるときは、3つのエージェントを順に切ります。

よくある質問

Claude Shipは誰が使えますか？

発表記事によると、ClaudeのTeamプランとEnterpriseプランで、GitHub上のリポジトリが対象です。データを保持しない設定、HIPAA向けの構成、顧客が管理する暗号鍵を使う組織では使えません。

AIが勝手に本番へ変更を入れることはありますか？

何がマージされるかは、利用者の設定とGitHubのブランチのルールで決まります。公式ドキュメントは、設定によっては、書いた本人以外の誰も見ないままマージされうると書いています。本線への直接のpushには、チェックが付きません。

観察モードなら費用はかかりませんか？

かかります。観察モードも課金されます。Claudeのレビューを使う方針は、観察モードでもCode Reviewを起動するためです。使用クレジットをオフにしても、有効なエージェントは動き続け、課金も続きます。

エンジニアが1人しかいない会社でも使えますか？

前提条件に、書き込み権限のある人が2人と書かれています。1人しかいないと、.claude/以下の変更や、Claudeのレビューが落ちたときに、チェックが通りません。導入の前に、この前提を満たせるかを確かめてください。

まとめ

Claude Shipの説明書は、書いた本人しか見ないまま変更が通りうる場合を、自分で7つ挙げています。止める力を持つのはGitHub側の設定です。明日やることは、自社のリポジトリの変更履歴を開いて、本線に入った変更のうち、プルリクエストを通したものと直接入れたものの数を数えることです。
