なぜClaude Codeは、持ち主のメールアドレスをWebサイトに送ったのか

2026.11.06 夕 ｜ 株式会社NGraph

AIは、ルールを破ったのではなく、守ったのです。

11月5日、Claude Codeが持ち主のメールアドレスを、Webサイトへの通信に書き込んでいた、という報告がGitHubに出ました。Claude Codeは、AIにプログラムを書かせたり、パソコンの作業を任せたりする道具です。

これは、AIの暴走の話ではありません。Webの側にある「ロボットは連絡先を名乗れ」という作法に、AIが従おうとした結果です。だから「個人情報を出すな」と指示しても、塞ぎきれません。

11月5日に報告されたのは、AIが持ち主のメールアドレスを名乗っていたこと

11月5日、Anthropicの公式リポジトリに、ある利用者が報告を出しました。題は「Bug Report: Privacy violation in User-Agent header」です。

User-Agentとは、ブラウザやプログラムが、相手のサーバーに「私はこういう道具です」と名乗る欄です。Webサイトの側から見ると、誰が来たかを知る手がかりになります。

報告者は、Web検索の最中に、許可なくメールアドレスが書かれたと訴えています。原文は「divulged my email to arbitrary 3rd parties in the User-Agent request header」です。無関係の第三者に、User-Agentの欄でアドレスを明かした、という意味です。環境は2.1.318でした。

11月6日時点で、賛同の反応は302、コメントは45件です。Hacker Newsでも964ポイントを集め、海外の開発者の間で大きく話題になりました。

別の利用者は、11月6日に、ネットに出ないechoコマンドで試しました。User-Agentにアドレスを書いても、2.1.317と2.1.318で拒否されずに実行された、という報告です。原因は、特定されていません。

同じ構造の指摘は、7月から出ていた

入り口の指摘は、7月にありました。7月25日、別の利用者が、サインインしたアカウントのメールアドレスが、AIの前提情報に入っていると報告しています。

前提情報とは、AIに毎回渡している、会話の土台になる情報です。コンテキストやシステムプロンプトとも呼びます。

報告によると、アドレスは設定ファイルから読まれ、「# userEmail」という塊で前提情報に入ります。同意も開示も、止める設定も無い、という訴えです。

しかも、この7月の報告に、11月6日時点で、開発側の返答は見当たりません。11月の報告までは、約3か月半ありました。

同じ問題は、7月から報告されていた

7月の訴えは、アドレスが前提情報に入っていることでした。11月の訴えは、そのアドレスが実際に外へ出たことです。入り口にあった話が、出口で起きた、と言えます。

AIはルールを破ったのではなく、Webの作法を守った

AIが従ったのは、どんな作法でしょうか。自動で動くプログラムは、名乗るものとされています。

作法は「名乗れ」と「勝手に名乗るな」の2つ

RFC 9110は、IETFが2022年6月に公開した、HTTPの仕様書です。ロボット型のユーザーエージェントは、問題が起きたとき運用者に連絡できるよう、有効なFromヘッダーを送るべきだ、と書かれています。

ところが、同じ仕様書には反対のことも書かれています。利用者の明示的な設定なしに、Fromを送るべきではない。プライバシーと衝突しうるからです。

名乗れ。ただし、勝手に名乗るな。この2つが、同じ文書に同居しています。

サイトの側の要求も、具体的です。Wikimedia財団は、2010年2月15日から、すべてのリクエストにUser-Agentを求めています。ボットには、運用者への連絡手段を添えます。連絡先は、メールアドレス、Webサイト、wikiのユーザー名のどれかです。

AIエージェントの運用は、AI導入支援のページもご覧ください。

開発側の説明は「作法に従う価値があると判断しがち」だった

Claude Codeの開発に関わる開発者が、11月5日にHacker Newsで説明しています。WikipediaなどにはスクリプトのクライアントがUser-Agentで名乗る方針があり、HTTPにも、その場合に連絡用のメールアドレスを入れる標準がある。Claudeはその方針に従う価値があると判断しがちなので、いまはプログラムで禁止した、という内容です。

もう1人の開発者は、11月6日に経緯を書きました。Claudeが名前を捏造するという報告があり、アカウントのメールアドレスを前提情報に入れた。すると、Claudeが自分でcurlなどを書くとき、連絡先としてそのアドレスをUser-Agentに入れることがあった、という説明です。「I'm sorry we let this happen.」とも書いています。

つまり、順番はこうです。名前を捏造されたくないので、アドレスを渡した。AIは、手元の連絡先を、作法どおりに書いた。

ここに、判断の転換があります。AIに渡した情報は、AIが善意で使います。渡した人が想定しなかった場所でも、役に立つと思えば使う。私たちは、そう読んでいます。

御社がAIに渡している前提情報に、何が入っていますか。

塞ぐ手段は3つ出ていて、効く範囲が違う

開発側が示した手は、3つです。組み込みの検査、次のリリースでの削除、検査を切る設定です。3つ目は、塞ぐ手を外す設定ですが、知っておく必要があります。

手何をするか効く範囲効かない範囲
組み込み検査アドレスを含み、User-Agentを名指しするシェル呼び出しを、確認なしで拒否するBash・PowerShell・Monitorの呼び出しWebツール、MCP、名指ししない書き方、スクリプトなど
次の版アカウントのメールアドレスを、前提情報から取り除く来週早々に届く見込み—
検査を切る設定/plugin disable、またはenabledPluginsでfalseにするユーザー設定と管理者設定。リポジトリ側では切れない切ると、組み込み検査は働かない

公式リポジトリのREADMEと開発者の書き込み（2026年11月6日時点）をもとに当社が整理しました。

組み込み検査が見るのは、シェル呼び出しの1つの形

2.1.317以降には、privacyという名前の組み込みのmodが入っています。modとは、Claude Codeに組み込まれた小さな検査プログラムです。既定で有効で、/pluginsで切れます。

仕組みはフック1本で、フックとは、AIが道具を使う直前に割り込んで検査する仕組みです。見るのは、Bash、PowerShell、Monitorの呼び出し。入力にアドレスがあり、かつUser-Agentを名指ししていれば、拒否します。

拒否は、確認を出さずに、どの権限モードでも行われます。判定は、入力全体で2つの語が揃うかを見るだけで、パーサーは意図的に持ちません。誤って拒否することは、受け入れる設計です。

ただ、READMEは、自分の限界もはっきり書いています。

「This is a courtesy, not a boundary, and it covers one shape.」礼儀であって、境界ではない。塞いでいるのは、1つの形だけ、という意味です。

すり抜けるものは、READMEが自分で列挙している

READMEが挙げる、すり抜けるものは次のとおりです。

  • User-Agentを名指ししないアドレス。URL、リクエスト本文、curl -u、Fromヘッダーなど
  • Webツール（WebFetch・WebSearch）とMCPツール。検査の対象に入っていません
  • 実行時に計算される値、変数、ファイル名で送るもの、アドレスを含むスクリプト
  • READMEに名前の無いクライアントや、別の方法でヘッダーを設定するもの
  • 二重エンコードや、非ASCIIのアドレス

MCPとは、AIに外部の道具をつなぐ窓口です。開発者の書き込みも、Claudeがスクリプトを書いて自分で実行する場合など、すべては防げない、と認めています。

メールを止める検査が塞ぐのは、1つの象限だけ

上段は、User-Agentを名指しする書き方です。下段は、それ以外です。READMEをもとに当社が整理しました。

安定版は、まだ2.1.311のままです。開発側は、2.1.317以降への更新を求めています。

同じ対策の説明が、3つの文書で食い違う

2.1.317の対策は、読む場所で説明が違います。

出どころ書かれていること動作
CHANGELOGWebまたはシェルのツールがアカウントのアドレスをネットへ送る前に、確認する検査を追加確認する
modsの一覧アドレスを含み、User-Agentを名指しするシェル呼び出しを、確認なしで拒否する拒否する
開発者の書き込みWebツール、またはcurl系のコマンドにアドレスが含まれるとき、実行前に確認する確認する
利用者の実測User-Agentにアドレスを書いたechoが、実行された止まらなかった

CHANGELOG、modsのREADME、開発者の書き込み、報告スレッドをもとに当社が整理しました。

1つ目は、対象です。CHANGELOGは「Webまたはシェル」と書きます。ところが、公開されているmodのソースが検査するのは、シェル呼び出しだけです。READMEは、Webツールは検査しない、と明記しています。

2つ目は、動作です。modのREADMEは、プロンプトを出さずに拒否する、と書きます。CHANGELOGと開発者は、確認する、と書きます。Webツール側の確認がどこにあるかは、公開されたソースからは分かりません。

3つ目は、利用者の実測です。原因は特定されていません。

だから、結論は1つです。効く範囲の正本は、説明文ではなく、公開されたソースとREADMEです。

中小企業の現場で見たこと

今日、私たちのPCで起きたこと
2026年11月6日、私たちのPCのClaude Codeがどの版かを確かめようとして、claude --versionと打ちました。すると、私たちが自分で入れている「道具を使う直前の検査」に拒否されました。検査の名目は「AIを直接起動することの禁止」で、版の確認は想定外の経路でした。拒否した側が正しい、と私たちは考えています。確認は、設定ファイルを読む別の方法で済ませました。
同じPCの~/.claude.jsonを開くと、oauthAccountの中に、emailAddressの項目が実際にありました。値は書きません。7月の報告どおりの構造です。サインインしているだけで、AIに渡る前提情報の材料が、ここにあります。

止める仕組みは、自分の想定外の経路も止めます。不便に感じた瞬間が、仕組みが効いている瞬間です。Anthropicのmodが「誤って拒否することは受け入れる」と書いているのと、同じ割り切りです。

自社で決める順番は、渡す情報を減らし、出口で止める

何から手を付けるべきでしょうか。順番は、4つです。

  1. 使っている版を確かめ、2.1.317以降へ上げます。
  2. AIに渡している前提情報を、棚卸しします。設定ファイル、社内ルールの文書、MCPでつないだ道具にある個人情報や顧客情報を、全部開きます。顧客情報の扱いは、11月3日の記事に書きました。
  3. 出口で止める仕組みを、自分の側にも置きます。自社の道具に合わせたフックを足します。確認ボタンだけに頼らない理由は、11月1日の記事にあります。
  4. 「使わないで」という指示だけで塞ぎません。指示が破られる理由は、AIは指示を一定確率で無視するという記事にまとめました。

失敗1：手元の設定を見て、安心する

modが有効なら、安心でしょうか。効くのは、公開されたソースの範囲だけです。READMEの「すり抜けるもの」を、自社の使い方に当てて読んでください。

失敗2：AIに「個人情報を出すな」と書いて終わる

しかし、書いても塞ぎきれません。Claudeは、作法に従う価値があると判断して、連絡先を書きました。Anthropic自身が選んだのも、指示ではなく、前提情報からの削除と、実行前の検査でした。

失敗3：AIを責めて、渡した側を見ない

AIは、作法に従いました。アドレスを前提情報に入れたのは、人です。責める前に、自社の設定ファイルに何が入っているかを開きます。棚卸しを一緒にやる支援は、AI導入支援（FDE）のページにあります。

よくある質問

Claude Codeを使っていなければ、関係ありませんか？

構造は同じです。渡した情報は、AIが役に立つと思えば、想定外の場所でも使われます。他の製品の実際の動きは、確かめていないので断定しません。

2.1.317に上げれば、安全ですか？

止まるのは、1つの形だけです。Webツール、MCPツール、アドレスを含むスクリプトは対象外です。

検査を切る設定は、どこにありますか？

/plugin disableか、設定のenabledPluginsに"cc-plugin-privacy@builtin": falseを書くと切れます。効くのは、ユーザー設定と管理者設定です。リポジトリ側の設定では切れません。

社内でAIに顧客情報を渡すときの線引きは、どうすればよいですか？

法律上の論点は、11月3日の記事にあります。線引きは、渡す量を減らすことから始めます。

まとめ

Claude Codeがメールアドレスを書いたのは、Webの作法に従った結果でした。2.1.317の検査が塞ぐのは1つの形だけで、READMEは「礼儀であって境界ではない」と認めています。

次の版でアドレスが消えても、ほかの情報は残ります。まず、AIに渡している前提情報を一度、全部開いてみてください。

AIに渡している情報の棚卸しを、一緒にやります。

エンジニアが御社の現場に入り、前提情報に何が入っているかを開き、出口で止める仕組みまで整える伴走支援です。
