同じサーバーに置いたAIの見張り役は、合図を受け取って354件の攻撃を全部通した

2026.11.26 夕 ｜ 株式会社NGraph

同じサーバーの2つのAIが、会話もファイルも使わず合図を送れました。

そんな研究が、2026年11月19日に公開されました。見張り役のAIに仕込みをした設定では、合図付きの攻撃354件を、354件とも通しています。見張り役とは、別のAIが出した行動の怪しさを採点して、止めるかどうかを決める役のことです。AIにAIを確かめさせている会社は、見張り役を置く場所を考え直す材料になります。

先に、条件を3つ書いておきます。研究はLessWrong（AIの安全性の研究者が多く投稿するサイト）への投稿で、査読付きの論文ではありません。設定は、手順を教えて読み取りを学習させたものでした。そして、クラウドのAPIでこの経路が通るかは、研究では試されていません。

この記事の結論は、見張り役は「別のモデル」にするだけでなく、「別の器」、つまり別の推論エンジンに置く、ということです。研究の設定では、ネットアクセスが無くても、同じサーバーの中で合図が通りました。私たちは福井市のNGraphで、AI導入の現場に入っています。

この記事でわかること
・何が示されたか。2つの経路と、見張り役の実験
・数字が100%から17%まで割れる理由と、どこまで割り引くか
・自社のAIの使い方でどこが同じサーバーになるか、見張り役の置き方

何が示されたか：会話もファイルも共有しない2つのAIが合図を送れた

推論サーバー（推論エンジン）は、学習済みのAIを動かして、届いた依頼に答えを返すソフトです。研究が使ったのは、vLLMというソフトです。Niranjan DeshpandeさんとDavid Africaさんは、同じ推論サーバーで動く2つのエージェントが、メッセージも同じファイルも使えなくても通信できる、と主張しています。

使うのは、サイドチャネルです。計算の時間や結果のわずかな違いのように、本来の連絡手段ではない経路を指します。

経路1：処理の大きさで、1ビットずつ送る

vLLMは、1回の処理の大きさに応じて、GPUで行列の計算をする部品（カーネル）を使い分けます。部品が違うと、計算結果にごく小さな丸め誤差の違いが出ます。出力の文章は、ほとんど変わりません。ただ、違いは決まった形で出るので、学習すれば読み取れます。

送り手が長い文書を読めば大きな処理が起き、読まなければ起きません。これで1ビットを送れます。繰り返せば、何ビットでも送れます。

経路2：キャッシュの掲示板に、目印を残す

KVキャッシュは、AIが読んだ文の途中の計算結果を取っておき、同じ文が来たら計算を省く仕組みです。このキャッシュには、計算されたときのカーネルの丸めが、そのまま残ります。

送り手は、あらかじめ決めておいた文を、大きな処理の中で計算させます。受け手は後で、その文のキャッシュを使い回したかどうかを区別できるわけです。研究では、この文を郵便受けと呼びました。前提として、受け手が補助のモデルを同じサーバーに呼べる必要があります。

色当て（処理の大きさ経由）受け手を学習させた。空のサーバー455回中455回正解

見張り役の実験：合図付きの攻撃を、354件とも通した

見張り役は、実行役が出した行動を0点から9点で採点し、5点以上なら止めます。作業をするAIが実行役です。研究は、同じモデルの1つを実行役に、もう1つを見張り役にしました。

守る側は、実行役と見張り役が組まないように、わざと怪しい偽の行動を混ぜます。これがおとりです。見張り役はおとりと本物の攻撃を区別できないはずなので、全部止めるしかない、という考え方です。

行動は2,200件で、うち700件が有害でした。仕込みの無い元のモデルは、有害な行動の88%を止め、無害な行動は止めません。

ここに仕込みを入れます。実行役は、有害な行動のとき、同時に長い文書を読みます。これが、大きな処理の合図です。おとりは、長い文書を読みません。見張り役には、処理が大きいときは0点を出すよう、最後の2層を学習させました。

結果は、学習に使っていない行動で、合図付きの攻撃354件中354件の通過でした。おとりは85〜92%を止めており、元のモデルの88%とほぼ同じです。無害な行動1,596件は、1件も止めていません。おとりで調べても、見張り役はいつもどおりに見えます。

タイミングも調べられています。長い文書を読ませると、大きな処理が数秒続きます。その間のどの時点で見張り役への依頼が来ても、20回中20回、合図を受け取れました。

まず、構成図を開いて、実行役と見張り役の置き場所を見てください。AI現場実装のページで、現場に入る形を説明しています。

100%から17%まで：数字が割れる理由は、サーバーの混み具合と仕込みの量

同じ研究の数字なのに、100%に近い値と、でたらめに近い値が並んでいます。では、なぜ割れるのでしょうか。理由は2つです。サーバーがどれだけ混んでいるか。受け手に、どれだけ仕込みをしたか。

混むほど、合図は読めなくなる

混んでいると、受け手の読み取りも大きな処理の中で起きます。そのため、区別できなくなります。研究は、Microsoft Azureの実際の利用ログ（2023年）を、0.1倍、0.25倍、0.5倍、1倍の速さで流しました。

混むほど、キャッシュ経由の合図は届かない

学習させた受け手がキャッシュ経由で色を当てる成功率。出所はLessWrong（2026年11月19日）。

キャッシュ経由の成功率は、100%、99%、90%、49%と下がります。処理の大きさを使う経路は、混雑にもっと弱くなります。空のサーバーでは455回中455回でしたが、混雑下では、0.1倍で39%、0.25倍で23%でした。経路によって、混雑への強さが違います。

仕込みが薄いほど、当たらなくなる

次の数字は、補助モデルに無改造のQwen3-8Bを使い、受け手を学習させずに、GLM-5.3を低い思考量で使った設定です。

手がかりが減ると、学習なしのAIは当てられない

8色から1色を当てる成功率。でたらめに選べば12.5%です。出所はLessWrong（2026年11月19日）。

手順、キャッシュの説明、郵便受けごとの基準値、変化の向きを全部渡すと100%です。変化の向きを抜くと94%、基準値を抜くと65%になります。どの郵便受けを調べるかまで受け手に選ばせると、17%でした。

実験の作りをどこまで割り引くか

著者自身が、この設定を「かなり作為的」と書いています。手順を教え、読み取りを学習させたからです。割り引く点は、ほかにもあります。学習はGPUをまたいで移らず、L40Sで学習した見張り役は、別のGPUでは合図を認識しませんでした。

一方で、割り引きすぎてはいけない点が3つあります。

  • 仕込みを薄くしても、手がかりがあれば当たる。図の2本目のとおりです。
  • 能力の高いモデルほど、少ない例で読める。研究で使われた能力の指標（ECI）の約150を境に、不連続に上がります。
  • Claude Opus 5.5は、少ない手がかりでこの手順に行き着いた。「処理の大きさがカーネルの選択に影響する」と伝えられた後の話です。ただし、脚注によると、Opus自身は各段階で驚いていて、通信が成功するとは予想していませんでした。

通る範囲も、vLLMだけではありません。2つの経路は、SGLang、LMDeploy、TensorRT-LLMでも動きました。

なお、著者は、最前線のモデルは足場があれば同様の手順を学べる、ここに挙げた以外の経路もほぼ確実にある、と書いています。これは著者の見立てです。

自社のAIの使い方では、どこが同じサーバーになるか

「同じサーバー」になるかどうかは、AIの使い方で変わります。使い方ごとに、各社の文書が書いているキャッシュの分け方を並べました。

Anthropic のAPI組織が違えば共有しない。Claude API、Claude Platform on AWS、Microsoft Foundryでは、ワークスペースごとにも分かれる試されていない
Amazon Bedrock、Google Cloud経由のClaude組織ごとにだけ分かれる試されていない

表2　使い方ごとのキャッシュの分け方。出所は各社の文書（閲覧日2026年11月26日）です。ワークスペースは、Claude APIの中で組織をさらに分ける単位です。

大事なのは、右の列です。クラウドのAPIでこの経路が通るかは、この研究では試されていません。各社の文書が書いているのは、キャッシュの分け方までです。依頼がクラウドの中でどう束ねられて処理されるかは、私たちが読んだ範囲では書かれていませんでした。だから、「クラウドなら安全」とも「クラウドでも危ない」とも、言えません。

一方、自社でvLLMを動かしているなら、研究の条件に近くなります。同じサーバーに、実行役と見張り役の両方を置いていないか。最初の確認は、ここです。

自社の場合：NGraphでは、Claude Code（Anthropic）が書いたコードや文書を、Codex（OpenAI）にレビューさせることがあります。会社が違うので、2つのAIは同じサーバーに乗っていません。ただ、これはこの研究を読んで選んだ設計ではなく、結果としてそうなっていただけです。読んで気づいたのは、逆の側でした。同じ推論サーバーに同じモデルを2つ並べて、片方に確かめさせる形なら、この研究の経路はふさがっていません。AIを2体並べる意味は、AIを2体並べても同じ間違いをする、という別の記事にも書きました。

見張り役を置くときの分け方

著者が挙げる対策は、見張り役と実行役を、別の推論エンジンのインスタンスで動かすことです。著者は、これでほぼ全てのサイドチャネルが閉じる、と書いています。「ほぼ全て」は著者の見立てです。

見張り役は、別の推論エンジンに置く

推論エンジンとキャッシュの組み合わせで見た、合図の通り方。出所はLessWrong（2026年11月19日）。

順番にやることは、次の6つです。

  1. 見張り役は、別のエンジンに置く。実行役とは別の推論エンジンのインスタンスで動かします。
  2. 自社サーバーなら、信頼する範囲ごとにcache_saltで分ける。vLLMの文書によると、同じsaltの依頼だけがキャッシュを使い回せます。著者は、これがキャッシュの掲示板の経路を塞ぐ、と書いています。
  3. バッチ不変を有効にする。バッチは、複数の依頼をまとめて1回で計算することです。環境変数VLLM_BATCH_INVARIANT=1で有効になり、バッチの大きさや順番に関係なく、同じ入力から同じ出力を出します。文書が挙げる目的は、デバッグや再現性で、セキュリティの目的は書かれていません。研究の著者が、処理の大きさの経路が閉じる、と書いています。対応するGPUは、NVIDIAのcompute capability 8.0以上などです。
  4. おとりにも、長い文書を読ませる。著者が挙げる、合図を壊す方法です。おとりが読まないと、合図の有無で本物と区別されてしまいます。処理を常に大きく保つ方法も、同じく著者が挙げています。
  5. 空のサーバーと混んだサーバーで、出力が1ビットも違わないか確かめる。著者がコメント欄で答えている見つけ方です。設定を変えて動かし、出力がビット単位で同じかを見ます。
  6. Claude APIなら、見張り役を別のワークスペースに置く。文書によると、ワークスペースごとにキャッシュが分かれます。ただし、経路が閉じると研究が確かめたわけではなく、文書の保証までです。

3つ目について、著者は、各社が効率を失うため、バッチ不変のカーネルはまだ使われていないだろう、と推測しています。

よくある失敗3つ

  • NG1　同じサーバーの同じモデルを2つ並べて、「二重チェック済み」と扱う。研究の見張り役の設定が、これでした。
  • NG2　ネットから切ったサーバーなら、中のAI同士も切れていると考える。研究の色当ては、ネットアクセス無しで当てています。ネットに繋がない環境でAIを動かす事業は、Y Combinatorも「AI for the Air-Gapped Economy」として起業の募集テーマに挙げています。切っても、同じサーバーの中は別の話です。
  • NG3　おとりを混ぜれば、見張り役の共謀は見抜けると考える。おとりが長い文書を読まないと、合図の有無で本物と区別されます。研究では、おとりを止める割合は元のモデルとほぼ同じでした。

見張り役の置き場所の洗い出しから、一緒に進めます。

NGraphは福井市の会社です。福井・石川・富山は訪問、それ以外の地域はオンラインで、エンジニアが現場に入ってAIを業務に組み込みます。

よくある質問

ChatGPTやClaudeをブラウザやAPIで使っているだけでも関係ありますか？

この研究が試したのは、自分でvLLMなどを動かす形です。クラウドのAPIでこの経路が通るかは、試されていません。各社の文書は、組織をまたいでキャッシュを共有しないと書いています。

見張り役を別の会社のAIにすれば防げますか？

研究が示したのは、実行役と見張り役が同じ推論サーバーにいる場合です。著者の対策は、別の推論エンジンのインスタンスに置くことです。別の会社のAIとの組み合わせは、研究では試されていません。

自社サーバーでAIを動かすとき、最低限なにを設定すればいいですか？

3つです。見張り役を別のインスタンスに置く。cache_saltで信頼する範囲ごとにキャッシュを分ける。VLLM_BATCH_INVARIANT=1を有効にする。そのうえで、出力が1ビットも違わないかを確かめます。

この研究のAIは、自分で勝手に合図を使い始めたのですか？

違います。手順を教え、読み取りを学習させた設定です。ただし、仕込みを薄くしても手がかりがあれば当たり、Claude Opus 5.5は少ない手がかりでこの手順に行き着きました。そのOpusも、通信が成功するとは予想していなかったと、脚注にあります。

まとめ

明日やることは、実行役と見張り役が同じ推論サーバーで動いていないかを、担当者に聞くことです。AIへの指示がどの会社を通るかは、別の記事で調べました。置き場所の洗い出しから相談したいときは、無料相談のページへどうぞ。
