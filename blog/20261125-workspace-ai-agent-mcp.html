Google Workspaceは2027年2月から、AIエージェントにGmailやDriveの通常のAPIを使わせない

2026.11.25 夕 ｜ 株式会社NGraph

Googleが、AIの通り道を1本に絞ります。

Googleは2026年11月25日、AIエージェントがWorkspaceにつなぐときは、専用のMCPサーバーかCLIを通すと発表しました。従来のAPIで直接つなぐやり方は、2027年2月1日から技術的に使えなくなります。つまり、メールやファイル、予定表にAIが触れる道の話です。

先に言葉を開きます。API（ソフト同士をつなぐ窓口）の従来の形を、REST APIと呼びます。MCPは、AIが外の道具やデータにつなぐための共通の差し込み口で、MCPサーバーはその差し込み口を用意する側です。CLIは、文字で命令する操作画面のことです。AIエージェントは、メールを読む、ファイルを探すといった複数の手順を、人の代わりに自分で進めるAIを指します。

この記事の結論は、中小企業が今やることは、使っているAIの連携が「どの許可の仕組みで、何に使われているか」を台帳にすることです。私たちは福井市のNGraphという会社で、AI導入の現場に入っています。

この記事でわかること
・何が、いつ変わるのか。日付と対象
・Googleのブログと規約で、書いてあることが違う3点
・同じ週のAnthropicとOpenAIの動き、自社で先にやること

2027年2月1日から、AIエージェントはMCPサーバーかCLIを通る

Google Cloud Blogの記事は、AIエージェントはREST APIではなく、MCPサーバーかWorkspace CLIを使わなければならない、と書いています。一方、会計ソフトのようなふつうのアプリは、これまでどおりREST APIで動き続けます。対象はAIエージェントだけです。

日付出来事書かれている場所
2026年11月24日Workspace AI Tools Addendum（規約の追加条項）が最後に更新された規約
2026年11月25日Googleが発表。MCPサーバーとCLIが一般提供になったブログ
2027年2月1日技術的な強制が始まる。AIエージェントは通常のAPIを使えなくなるブログ
2027年4月1日利用枠の課金が始まるブログ

表1　発表と強制の日程。出所はGoogle Cloud Blog（2026年11月25日）とGoogleのWorkspace AI Tools Addendum（最終更新2026年11月24日）

対象の製品も見ておきます。一般提供になったMCPサーバーは、Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat、Tasksの8製品です。CLIは、手元のパソコンで動くエージェント向けで、こちらも一般提供です。

ただし、2月と4月の日付が書かれているのは、ブログだけです。規約の側には、最終更新日以外に日付がありません。この違いは、2つあとの章で扱います。

気になるのは、自社が組んだAIの連携が、どちらの道を通っているかです。ここが分からないまま2月を迎えるのが、いちばん困ります。AI現場実装のページで、現場に入る形を説明しています。

Googleが通り道を1本にする背景を、数字で見る

Googleは、WorkspaceのAPIが月に2.8兆回を超えて呼ばれていると書いています。Drive APIの公開トラフィックだけで、2022年の2.5倍超です。Driveからの読み取りは、1日180億回超がAPI経由です。

DriveのAPI量は、2022年の2.5倍を超えた

Google Cloud Blog（2026年11月25日）が書く、Drive APIの公開トラフィックの量。2022年との比較です。

では、なぜ1本にするのでしょうか。通り道が多いと、確認する場所も散らばります。1本にまとめれば、毎回同じ確認が掛かる形になります。ブログによると、MCPサーバーとCLIには次のものが入っているそうです。

  • 権限の確認。AIが触ってよい範囲かを、その場で確かめます。
  • 情報漏えい防止の検査。DLPと呼ばれる、出してはいけない情報が外へ出ないかの検査です。
  • 人の確認。次の節で書く操作の前に、利用者に確かめます。
  • プロンプト注入の検査。メールや文書に紛れた命令でAIを操る攻撃への備えで、Google CloudのModel Armorと連携します。
  • AIエージェントの分類。AIとして分類されていないOAuthクライアントは、MCPサーバーが断ります。OAuthは「このアプリに自分のアカウントを触らせてよい」と許可する仕組みで、クライアントはその許可を受けるアプリ側の登録です。

管理者は、管理コンソールでAIエージェントを一覧し、監査し、取り消せます。Googleは、20年以上、40億人の利用者と1,300万の組織を守ってきたと書いています。

人の確認が要る操作と、自動で動く操作

ブログによると、エージェントがメールを送る前、Driveの共有の権限を変える前、まとめて編集する前に、MCPサーバーとCLIは利用者の明示的な確認を求めます。一方、下書きの作成や文書の要約は、確認なしで自動で動きます。

人の確認が要るのは、送信・共有変更・一括編集

上の段が人の確認が要る操作、下の段が自動で動く操作です。出所はGoogle Cloud Blog（2026年11月25日）。

Googleは、まだ出ていない機能も挙げています。時間を区切った承認、特定のメールやファイルにエージェントを近づけない設定、利用者が操作を見て取り消せる機能です。いずれも「まもなく」で、時期は書かれていません。

ブログと規約で、書いてあることが少しずつ違う

同じ話が、ブログと規約の2か所に書かれています。では、何が違うのでしょうか。読み比べると、3点が少しずつ違います。

  1. 通り道の名前。ブログは「MCPサーバーかCLI」と書きます。規約で「必ず使う」と定める条文は、Google MCPだけを名指ししています。ただし、規約の定義の側には、コマンドラインも出てきます。
  2. 日付。2027年2月1日と4月1日は、ブログにだけあります。規約にあるのは、最終更新日の2026年11月24日だけです。
  3. 取り消しの速さ。ブログは、Google Cloud側のエージェントについて、Agent IdentityかOAuthの許可を取り消せば、アクセスはすぐ止まると書いています。Workspace側については、管理コンソールで一覧、監査、取り消しができる、という書き方です。前者の「すぐ止まる」を、そのままWorkspaceに当てはめるのは早い読み方です。

理由は、書く目的が違うからだと私たちは読んでいます。ブログは、全体像を伝える発表です。一方、規約は法的な約束です。そのため、守る条件は規約で、日付と全体像はブログで読む。この分け方が安全です。

ただし、CLIが規約の上でどう扱われるかは、条文だけでは確定できませんでした。判断の前に、提供元とGoogleの最新の規約で確かめてください。

規約には、AIツールの側に課される禁止もあります。次の6つです。

  • 利用者が許可した作業以外に、利用者のデータを処理すること
  • Googleの技術情報を、30日を超えて保存すること
  • 接続を切った、または取り消した後に、データを残すこと
  • 体系的なスクレイピング（自動で大量に読み取ること）
  • モデルの学習、微調整、評価データ作り、蒸留に使うこと
  • Workspaceに似た製品を作るのに使うこと

違反とGoogleが合理的に判断すれば、Googleは、ツールのアクセスをすぐに制限、削除するか、利用者のアクセスを停止、終了できると、規約にあります。

同じ週に、AnthropicとOpenAIも、守りをモデルの外に置く仕組みを出した

2日前の11月23日に、AnthropicとOpenAIも、守りの置き場所に関する発表をしています。3つは別の話です。ただ、「AIの賢さに頼らず、AIの外に検査を置く」という向きは重なります。

発表どこで守るか何を見るか状態
Google 11月25日AIとWorkspaceの間の通り道。MCPサーバーとCLI権限、情報漏えい、人の確認、プロンプト注入MCPサーバーとCLIは一般提供。強制は2027年2月1日から
Anthropic 11月23日顧客自身のストレージの中。S3かGoogle Cloud Storage多数のリクエストをまたいだ不正利用のパターン公開ベータ
OpenAIとCisco 11月23日動いているLinuxの中脆弱なコードの経路を、一時的に塞ぐオープンソース。「最初の一歩」

表2　3社の発表の比べ方。出所は各社の発表（2026年11月23日、25日）

Anthropicの仕組みは、Enterprise Frontier Safeguards、略してEFSといいます。1回1回のやり取りではなく、多数のリクエストをまたいだ不正利用のパターンを、自動で見張ります。検知は顧客自身のストレージで行い、Anthropicもクラウド事業者も、企業のデータを保存しません。これをゼロデータ保持と呼びます。リスクを見つけると「Safety Case」を作りますが、入出力は含まず、運営者が中身を人の目で見ることも、学習に使うこともありません。

Anthropicは9月に発表済みで、Fortune 100の4分の1を含む100社超の顧客と開発したと書いています。挙げられた例は、9月にあった、約50の組織を狙い、作業を並列のエージェントに分けた攻撃です。提供先は、Claude Platform、AWS上のClaude Platform、Amazon Bedrock、Google Cloud上のClaudeで、Microsoft Foundryは近日です。

OpenAIとCiscoのShirudoは、オープンソースのランタイムです。動いているLinuxに、再起動せずに一時的な「盾」をかけ、脆弱なコードの経路を塞ぎます。盾は、運用者が承認してから有効にし、読み込む前に暗号で署名を検証します。

管理された試験では、Codexが作った盾が、動いているElasticsearchへのJava4Shellの攻撃の試みを、再起動なしで防ぎました。OpenAIは、パッチの試験と展開には、まだ数日から数週間かかることがあると書き、この仕組みを「最初の一歩」と位置づけています。名前は、日本語の「シールド」から付けたそうです。

この2つは、AIの道具を選ぶときの物差しとして読めます。検査がどこに置かれているかを、提供元に聞く理由になります。

中小企業の判断はどう変わるか。やりがちなNG3つ

これまでは、AIツールの「何ができるか」を主に見ていました。これからは、何を聞けばよいのでしょうか。「どんな道でWorkspaceにつながるか」も、同じ重さで聞くことです。

自社の場合：うちにも10月13日、Googleから「Action Required」のメールが届きました。社内の知識ベースのために作ったGoogle CloudのプロジェクトのOAuthクライアントを、「AIエージェント」に分類するかを決めてほしいという内容で、期限は11月11日でした。分類しないクライアントは、WorkspaceのMCPサーバーを呼べなくなる、とありました。手を止めたのは、分類そのものではありません。どのクライアントが何に使われているかを、1つずつ確かめる所でした。作った時は1つの用途だったものが、いつの間にか複数の連携に使い回されています。今回の発表は、その台帳を先に作れという話だと読みました。
  • NG1　AIツールに、社員個人のGoogleアカウントで広い権限を許したまま放置する。これからの前提は、AIエージェント専用のOAuthクライアントと、最小の権限です。
  • NG2　「メールを勝手に送らない」を、AIツール側の設定だけに頼る。ツール側の設定は、Workspaceの外にあります。人の確認がWorkspace側で掛かる通り道へ寄せておくと、設定に左右されません。
  • NG3　2027年4月の利用枠の課金を見ないまま、常時同期の連携を組む。課金は4月1日に始まると、ブログにあります。料金の金額は、ブログには書かれていません。量の多い連携から先に洗い出しておきます。

よくある質問

会計ソフトなど、ふつうのアプリの連携も止まりますか？

ブログは、従来のアプリは既存のREST APIで動き続けると書いています。対象はAIエージェントです。

いつまでに何をすればいいですか？

技術的な強制は、2027年2月1日から始まります。それまでに、AIの連携をMCPサーバーかCLIへ移します。

料金はかかりますか？

利用枠の課金は、2027年4月1日から始まるとブログにあります。金額は、ブログには書かれていません。

AIツールに渡したWorkspaceのデータは、どう扱われますか？

規約は、Googleの技術情報を30日を超えて保存すること、モデルの学習などに使うこと、接続を切った後に残すことを禁じています。詳しい6つは、本文の規約の章に挙げました。

まとめ

Googleは、2027年2月1日から、AIエージェントにMCPサーバーかCLIを通させます。ブログと規約は、通り道の名前、日付、取り消しの書き方で、少しずつ違います。明日やることは、管理コンソールでAIエージェントの一覧を開き、どのOAuthクライアントが何に使われているかを書き出すことです。
